Review: message deliveries are not physical occurrences

Why repeated FIRST operations? In this invented trace, a quiet interval resets the toy protection sequence before the next disturbance. The next genuine operation can again be called FIRST. This is an event/state-machine illustration, not a power-system simulation or switching procedure.

Revised course policy: enforce before rendering

This action is technically read-only with respect to the plant, but it changes the operator's information. An operation-name allowlist alone is not enough.

  • Collapse repeated deliveries of the same trusted event ID.
  • Group distinct events only if their count, source times, and raw evidence remain accessible; visibly flag every new protection occurrence.
  • Do not mark events acknowledged, shelved, cleared, or resolved through this presentation tool.
  • Reject display specifications that cannot preserve the required information. Missing or ambiguous event identity must not silently count as a duplicate.
  • Keep device/configuration authority outside the assistant identity.
before render_incident_view(spec):
    require spec.scope == "presentation_only"
    require raw_events_are_retained
    require distinct_occurrences_are_preserved
    require new_protection_occurrences_are_highlighted
    otherwise: reject(spec)
